# s4cred — Implementation Plan

**Status:** Released as v1.0.0. Go tests with the race detector, browser tests, and the container smoke test passed before the tag. No container image was published to a registry, and public deployment was not performed.

**Goal:** Build a containerized application for sharing single-use notes encrypted in the browser.

**Specification:** `docs/requirements.md`, particularly the agreed requirements, technical defaults, threat model, and acceptance criteria.

**Stack:** Go 1.27.3+, SQLite via `modernc.org/sqlite` v1.40.1, `net/http`, Web Crypto, HTML/CSS/JavaScript, Docker, and an HTTPS reverse proxy.

## Before Starting

1. Review the agreed product requirements and technical defaults; incorporate any additional user feedback.
2. Select and verify the SQLite driver against the required deployment and concurrency constraints.
3. Prepare adaptable deployment examples for all three reverse proxies; the actual public domain and deployment topology can be supplied at deployment time.
4. Pin the Go toolchain and dependency versions; select supported, regularly updated build and runtime images.
5. Begin implementation only after explicit user approval.

## Phase 1 — Data Model and Single-Use Reads

**Deliverable:** Local SQLite storage, independent of the HTTP interface.

- [ ] Create the schema with identifier hash, read-token hash, ciphertext and nonce as BLOBs, and expiration; configure connections and secure deletion.
- [ ] Store a record and enforce both the active-note count and ciphertext-byte limits in one transaction; exclude expired notes and validate expiration options against the allowed list.
- [ ] Implement atomic retrieval and deletion, validating expiration and comparing the supplied read-token hash in constant time within the transaction. Missing or invalid tokens must not consume the record; commit before returning ciphertext.
- [ ] Delete expired records on startup and periodically; reads must reject expired records regardless of cleanup status.
- [ ] **Verification:** Go storage tests cover creation, missing or incorrect tokens followed by a successful read, second read, expiration, cleanup, count and byte capacity limits, and concurrency. Exactly one concurrent authorized reader receives a record; concurrent writes exceed neither capacity limit. Verify that a note expiring while waiting for the write lock is not returned. Run the relevant tests with Go's race detector.

## Phase 2 — HTTP API and Request Security

**Deliverable:** API matching the table in `docs/requirements.md`.

- [ ] Provide create and confirmed-consume endpoints with stable non-sensitive error codes for browser localization. Store only the read-token hash on creation; require the raw token in the consume request body. Unify the response for missing, expired, previously consumed, and unauthorized notes.
- [ ] Read and bound the complete request before changing data; accept exactly one JSON object with no duplicate fields or trailing values. Validate types, allowed lifetime, base64url syntax, decoded ciphertext length, total request size, and origin. Allow a 1,000,000-byte UTF-8 note plus the AES-GCM tag and encoding overhead; document that the server cannot validate encrypted plaintext.
- [ ] Add privacy and security headers; disable logging of sensitive paths, data, and error details.
- [ ] Ensure `GET /n/{id}` does not check, fetch, or delete a note.
- [ ] **Verification:** Go HTTP tests cover the contract, invalid data and sizes, oversized chunked and trailing request bodies, duplicate fields, missing, malformed (including wrong JSON types), and incorrect read tokens without consumption, a valid token after rejected attempts, maximum-size ciphertext, missing or foreign origin, headers, absence of data leakage, and GET requests not consuming notes. Run the relevant tests with Go's race detector.

## Phase 3 — Browser Interface and Encryption

**Deliverable:** Complete sender and recipient flows without external resources.

- [ ] Build the text form, lifetime selector, optional-password checkbox and password confirmation fields, 1 MB UTF-8 validation, messages, link view, and copy support with manual selection fallback.
- [ ] Create a friendly, futuristic and responsive interface with dark mode as the default, a light-mode switch, accessible contrast and keyboard controls, and reduced-motion support. Persist explicit theme preferences locally where possible.
- [ ] Add complete English and Polish translations, browser-preference detection with regional-variant support and an English fallback, plus a visible language selector. Persist explicit language selection locally where possible; never use IP geolocation or translate note contents.
- [ ] Independently generate the encryption key, nonce, and read token through Web Crypto. Encrypt the note with AES-256-GCM and send the token hash on creation. For password-protected links, wrap the key and token together with a password-derived key as described in the versioned specification; the password must not reach the link or server.
- [ ] Build the recipient page with a warning, password field when needed, and confirmation button; validate the fragment and, for password-protected links, decrypt the key and token locally before sending the token in the consume request body. After retrieval, decrypt and display text without interpreting HTML.
- [ ] Handle missing Web Crypto, unavailable notes, network and decryption errors, and unavailable clipboard access. Clearly explain when a note may be irreversibly consumed.
- [ ] **Verification:** Use fixed interoperability vectors for both fragment formats, decoded field lengths, PBKDF2 parameters, NFC passwords, and AES-GCM. Real-browser tests cover flows with and without a password, mismatched password confirmation, an incorrect password without a consume request or consumption, retry with the correct password, Unicode encryption and decryption, 1,000,000-byte and 1,000,001-byte boundaries, repeated GET without consumption, confirmed read, second read, missing and incorrect keys and tokens, network errors, manual copying, and non-execution of injected HTML. Verify Polish and English browser locales, unsupported-locale fallback, manual language switching, dark default and light switch, preference persistence and unavailable storage, keyboard navigation, contrast, and reduced motion. Network inspection confirms that passwords, encryption keys, and plaintext do not reach the server and that the raw read token appears only in the confirmed consume request body.

## Phase 4 — Container and Secure Deployment

**Deliverable:** Repeatable deployment of one instance with a persistent volume.

- [ ] Prepare a multi-stage Go image with pinned dependencies, a non-root user, appropriate data-directory permissions, and no unnecessary files or Python runtime.
- [ ] Prepare `compose.yaml` with a named volume, public-origin settings, count and byte quotas, and localhost port binding.
- [ ] Prepare separate examples for Nginx, Traefik, and Caddy: HTTPS, HSTS, limits allowing a valid maximum-size request, no consume retries, safe forwarding-header handling, and no sensitive URL or request-body logging. Document any controls each proxy cannot provide directly and the required compensating controls; examples must not require privileged Docker socket access.
- [ ] **Verification:** Build the image; validate and exercise each of the three proxy examples with the application, including HTTPS, process user, request, rate and connection limits, request timeouts, logging behavior, spoofed forwarding headers, and consume retry settings. Verify that direct access cannot bypass the intended proxy where the deployment topology requires it. Record any example or control that could not be verified. Create a note, replace the container with the same volume, and read it only once.

## Phase 5 — Documentation and Final Review

**Deliverable:** An operator can deploy the service and acceptance criteria have been checked.

- [ ] Document startup, HTTPS requirements, configuration, volume permissions, upgrades, count and byte limits, SQLite storage overhead, and capacity monitoring.
- [ ] Document the threat model, link leaks, read-token protection and its limitations, a separate password channel, offline password guessing, server trust limitations, clock synchronization, irreversible read failures, physical deletion limitations, and backup risks.
- [ ] Run the full Go test suite, including the race detector, browser flow, and container replacement test; record results and anything not verified.
- [ ] Check every criterion in section 9 of `docs/requirements.md`; inspect logs and database contents for plaintext, keys, raw read tokens, and complete links.
- [ ] Present results and remaining risks to the user. Do not publicly deploy or publish an image without a separate user decision.
