# Nginx HTTPS example

This is a standalone Nginx configuration for a proxy on the same host as Compose. It starts on `127.0.0.1:443`; it is **not publicly reachable by default**. Obtain and renew a trusted certificate separately. Replace `notes.example.com` and the certificate paths in `nginx.conf`, set the app's `PUBLIC_ORIGIN` to `https://notes.example.com`, and install the two files as `/etc/s4cred/nginx.conf` and `/etc/s4cred/nginx-proxy.conf`. Ensure Nginx can read the certificate and private key. Validate with `nginx -t -c /etc/s4cred/nginx.conf`, then start with `nginx -c /etc/s4cred/nginx.conf`. Use your service manager for lifecycle management.

For public service, bind the HTTPS listener to the intended public interface only after reviewing the controls below and firewall rules. Configure DNS and use a valid certificate. This example does not listen on port 80 or obtain certificates. If Nginx is containerized or remote, adapt `proxy_pass` to a private reachable app address and secure that network; `127.0.0.1` is local to Nginx's namespace.

- A 1,400,000-byte body limit, separate per-client create/read rates (10/minute and 60/minute, with bursts of 10 and 60), and 20 concurrent connections per client are configured. The rate zones are leaky-bucket limits, not strict rolling-window counters; tune bursts and limits for actual use. `/api/notes/` is limited as reads regardless of method.
- Body buffering is set to the maximum body size, but verify your Nginx build, memory pressure and request-body temporary-file behavior. Protect any temporary storage: requests can contain a raw read token.
- Nginx's header, body, upstream and send timeouts are **inactivity** timeouts, not an absolute request-duration cap. Configure a hard total request-duration limit at a trusted edge or in the application before public deployment.
- `proxy_next_upstream off` disables Nginx upstream retries. Idempotency headers are removed; disable retries in all other intermediaries and clients as well. A failed delivery can still consume a note.
- The direct peer is the rate-limit identity. Only required application headers and Nginx-generated forwarding headers reach the app; client-supplied forwarding headers are discarded. The app validates the configured origin rather than trusting them. Behind a load balancer, configure Nginx real-IP handling only for explicit trusted proxy CIDRs, make that proxy strip client-supplied headers, and restrict direct access. Otherwise all users share the proxy's limit or client addresses may be spoofed.
- Access logs and error logs are discarded because Nginx errors can include request paths. Monitor process health separately. Ensure the service manager, CDN, WAF, and other intermediaries do not capture paths, referers, request bodies, or tokens; do not enable debug logging. Audit logs and temporary storage before exposure.
