# Caddy HTTPS example

Use Caddy 2.10 or newer on the Compose host. This example uses supplied certificate files and binds `127.0.0.1:443`, not a public interface. Replace `notes.example.com` and the certificate paths in `Caddyfile`; set the app's `PUBLIC_ORIGIN` to `https://notes.example.com`. Ensure Caddy can read the files, validate with `caddy validate --config /etc/s4cred/Caddyfile --adapter caddyfile`, then run `caddy run --config /etc/s4cred/Caddyfile --adapter caddyfile >/dev/null 2>&1` under a service manager with equivalent output suppression. Obtain and renew certificates separately; automatic HTTPS and the admin API are disabled in this example.

**Before public exposure:** standard Caddy provides neither the separate per-IP creation/read rate limits nor a per-IP connection limit configured here. Install a trusted edge/WAF or carefully vetted Caddy modules that enforce both (starting points: 10 creates/minute, 60 reads/minute, 20 connections per IP); test them with your actual topology and HTTP/2. Only then change the listener bind and firewall, and configure DNS and a valid certificate. If Caddy is containerized or remote, change the upstream to a private reachable application address and secure that network.

- `/api/files` allows 33,562,644 bytes. Other routes stay at 1,400,000 bytes; the app must also enforce its own limit. Caddy rejects a larger `Content-Length` before proxying and streams an accepted body through a small read buffer instead of holding the upload in memory. The application then spills that body out of its own small copy buffer into a temporary file. Server read-header, whole-body, write and idle timeouts and upstream dial and response-header timeouts are configured (`read_body` and `write` are 120 seconds; the file route waits 120 seconds for response headers, and other routes wait 30). Tune for legitimate slow clients. Temporary files can hold ciphertext and sealed packages. Ten file creations per minute can write about 320 MiB per minute per IP before the committed quota rejects more.
- No load-balancing retries are configured, and idempotency headers are removed. Disable retries in all other intermediaries and clients too. A failed response can still consume a note. Consume responses for files must not be retried.
- Caddy does not trust upstream proxies by default; it replaces untrusted `X-Forwarded-For`, `X-Forwarded-Proto`, and `X-Forwarded-Host`. `Forwarded` and the additional headers listed in the Caddyfile are stripped. Arbitrary vendor-specific forwarding headers are not generically filtered; the app must not trust them. The app uses its configured origin, not forwarding headers. If behind a load balancer, restrict direct access, configure only its exact trusted CIDRs and strict client-IP parsing, and ensure it strips client-supplied forwarding headers. Enforce rate limits using the correct verified client IP.
- No access logger is configured, and Caddy's default logger is discarded to avoid request-bearing errors. A logged `/n/{code}` is enough to open an unprotected note. Monitor process health and certificate expiry separately. Ensure the service manager, edge, CDN, WAF and other intermediaries do not capture paths, referers, request bodies or tokens. Do not enable debug logging; audit after changes.
